## 1. 이번 작업에서 확인한 구현 원칙

정보처리기사 실기 합격 코치는 Sentence의 학습 UX 원칙만 참고하고 학습 콘텐츠와 기억 이력은 별도 제품 경계로 유지한다. 기존 `@newsorder/db`의 사용자·진도·콘텐츠 테이블을 재사용하지 않는다.

첫 개인 MVP는 SQL과 C 언어의 얇은 전체 목차가 아니라 다음 흐름이 끝까지 이어지는 수직 범위를 목표로 한다.

1. 공식 범위 연결
2. 짧은 이해 자료
3. 도움 없는 첫 제출
4. 규칙 기반 채점
5. 즉시 교정과 점진적 힌트
6. `Again / Hard / Good / Easy` 회상 평가
7. FSRS 다음 복습 계산
8. 만기 복습 우선의 오늘 큐
9. 취약점과 준비도 리포트

오답 또는 힌트를 사용한 정답은 성공한 회상으로 기록하지 않고 반드시 `Again`으로 처리한다. 사용자가 작성한 SQL·코드·서술 답안 원문은 장기 학습 이벤트에 저장하지 않는다.

## 2. 실제로 만든 첫 프로토타입

첫 시도에서는 `apps/exam-coach`라는 독립 Next.js 앱을 추가했다. 이 프로토타입은 최종적으로 저장소에 남기지 않았지만 아래 구조와 계약을 실제 코드로 작성하고 lint까지 확인했다.

### 2.1 제품 셸과 화면

다음 5개 화면의 정보 구조를 구현했다.

- `오늘`: 시험일과 하루 학습 가능 시간을 받고 만기 복습과 신규 학습을 배치
- `커리큘럼`: 공식 12개 영역과 현재 SQL·C 수직 범위를 분리해 표시
- `취약점`: 오답, 힌트 사용, `Again` 이력을 카드별로 집계
- `모의고사`: 주간 미니 테스트와 150분 전체 모의고사를 정규 기억 일정과 분리하는 구조
- `리포트`: 콘텐츠 커버리지, 독립 회상 성공률, 복습 부채를 별도 지표로 표시

리포트에는 근거 없는 합격 확률을 만들지 않도록 했다.

### 2.2 공식 범위 레지스트리

2026 정보처리기사 실기 범위를 기준으로 12개 상위 영역 식별자를 코드에 정의했다.

1. 요구사항 확인
2. 데이터 입출력 구현
3. 통합 구현
4. 서버프로그램 구현
5. 인터페이스 구현
6. 화면 설계
7. 애플리케이션 테스트 관리
8. SQL 응용
9. 소프트웨어 개발 보안 구축
10. 프로그래밍 언어 활용
11. 응용 SW 기초 기술 활용
12. 제품 소프트웨어 패키징

개인 검증 콘텐츠는 이 중 `SQL 응용`과 `프로그래밍 언어 활용`에만 연결했다.

### 2.3 SQL·C 콘텐츠 수직 범위

프로토타입에는 6개 학습 단위와 7개 회상 카드를 작성했다.

SQL:

- `WHERE`의 역할 설명
- `WHERE` 조회문 직접 작성
- `WHERE`와 `HAVING` 구분
- `INNER JOIN`의 결과 행 기준 설명

C:

- `for` 반복문 출력값 추적
- 배열 인덱스와 출력값 추적
- 포인터와 역참조에 따른 값 변화 추적

각 단위에는 공식 영역 ID, 개념 ID, 콘텐츠 버전, 선수 개념, 학습 목표, 설명, 예시, 힌트, 채점 규칙을 두는 형태를 검증했다.

### 2.4 첫 제출과 채점 정책

첫 제출 전에는 힌트와 정답을 보여주지 않고 제출 이후에만 교정 흐름을 열도록 구현했다.

채점기는 다음 세 가지 규칙을 지원하도록 만들었다.

- `exact`: 출력값처럼 정확한 값 비교
- `keywords`: 개념 서술에서 필수 핵심어 확인
- `sql`: 필수 SQL 요소와 금지 SQL 요소를 규칙으로 검사

SQL은 문자열 전체 일치가 아니라 공백·세미콜론 차이를 정규화하고 필수 구조를 검사하는 방향을 사용했다. 데이터 변경이 필요 없는 조회 문제에서는 `DELETE`, `UPDATE`, `INSERT` 같은 금지 토큰을 차단하도록 했다.

### 2.5 학습 이벤트

프로토타입의 장기 저장 단위는 답안이 아니라 불변 학습 이벤트였다. 이벤트에 포함한 핵심 값은 다음과 같다.

- 중복 방지 이벤트 ID
- 발생 시각
- 회상 카드 ID
- 콘텐츠 버전 ID
- 첫 제출 정답 여부
- 회상 등급
- 응답시간
- 도움 사용 여부
- 신규 학습/복습 구분
- 기억 알고리즘 버전

브라우저 게스트 단계에서는 별도 namespace의 `localStorage`에 이 이벤트와 학습 계획만 저장하는 구조를 사용했다. 작성한 답안 원문은 저장하지 않았다.

### 2.6 FSRS와 기억 상태

처음에는 기억 일정 계약을 빠르게 검증하기 위해 임시 수식을 작성했지만, 제품 문서의 “유지보수되는 검증된 FSRS 구현을 고정한다”는 조건에 맞지 않아 제거했다.

이후 `ts-fsrs@5.4.1`을 어댑터 뒤에서 사용하는 방식으로 교체했고 다음 설정을 검증했다.

- 목표 기억률: `0.9`
- 최대 간격: 36,500일
- 이벤트의 회상 등급을 FSRS `Rating`으로 변환
- 카드 상태를 최종 값으로 저장해 신뢰하지 않고 이벤트를 다시 재생해 계산

동일 ID의 이벤트는 한 번만 반영하고, 입력 배열 순서와 관계없이 발생 시각 순으로 재생하도록 했다.

### 2.7 오늘 큐

오늘 큐는 다음 순서로 구성했다.

1. FSRS 기준 만기 복습 카드 계산
2. 기억 위험도, 연체 정도, 콘텐츠 중요도, 시험 임박도를 이용해 복습 우선순위 계산
3. 복습을 먼저 하루 시간 예산에 배치
4. 남은 시간에 선수 개념이 충족된 신규 카드 배치

SQL에서는 `sql.where` 학습 뒤 `HAVING`과 `JOIN` 개념이 열리고, C에서는 반복문 이후 배열, 배열 이후 포인터가 열리는 선수지식 그래프를 검증했다.

## 3. 작성했던 자동 검증

프로토타입에는 다음 단위 테스트를 작성했다.

- SQL 공백 차이를 허용하면서 필수 구조를 판정하는지
- 조회 문제에서 금지 SQL을 거부하는지
- 개념 서술의 필수 핵심어 누락을 잡는지
- 오답은 요청 등급과 관계없이 `Again`이 되는지
- 힌트를 사용한 정답도 `Again`이 되는지
- 동일 이벤트가 중복 재생되지 않는지
- 이벤트 입력 순서가 뒤섞여도 시간순으로 기억 상태를 재계산하는지
- 선수 개념이 없는 SQL/C 카드를 최초 큐에 넣는지
- 선수 개념 학습 뒤 다음 개념이 열리는지
- 만기 복습이 신규 카드보다 먼저 배치되는지

Playwright 시나리오도 다음 흐름으로 작성했다.

- 게스트가 시험일과 하루 학습 시간을 설정
- 오늘 큐에서 첫 학습 시작
- 답안 제출
- 정답 피드백 확인
- `Good` 기록
- 저장된 이벤트에 답안 원문이 없는지 확인
- 초기 화면의 axe `serious`/`critical` 접근성 위반 확인

## 4. 실제 검증 결과

개발 중 확인한 주요 결과는 다음과 같다.

- 새 앱을 포함한 전체 workspace ESLint는 소스 오류 없이 통과했다.
- React 19 purity 규칙 때문에 렌더 중 `Date.now()`를 호출하던 코드를 발견했고, 사용자 입력이 시작되는 이벤트 시점에 측정하도록 수정했다.
- 모의고사 화면의 JSX 닫힘 오류를 발견하고 수정했다.
- `ts-fsrs@5.4.1` 추가 시 저장소 공급망 검사는 패키지를 허용했다.
- Drizzle 스키마 검사 자체도 기존 DB에 대해 성공했다.

다만 저장소 writer의 “검사 도중 작업트리가 변경되면 실패” 규칙 때문에 전체 필수 게이트 완료까지 진행하지 못했다.

## 5. 프로토타입을 되돌린 이유

현재 저장소는 pnpm workspace를 사용한다. `apps/exam-coach`를 새 workspace로 추가하면 검사 실행 중 pnpm이 `pnpm-lock.yaml`에 새 importer를 자동 생성한다.

Git writer는 `pnpm-lock.yaml`을 보호 경로로 취급하고 있어 이 자동 변경을 일반 소스 패치와 같은 방식으로 확정할 수 없었다. 그 결과 각 검사 명령 자체는 성공해도 작업트리가 변경된 것으로 판정되어 전체 게이트가 실패했다.

이 상태에서 불완전한 앱 코드만 남기거나 lockfile을 우회하는 것은 저장소 정책과 재현 가능한 CI 원칙에 어긋나므로 `apps/exam-coach` 프로토타입과 자동 생성된 lockfile 변경을 모두 되돌렸다.

## 6. 후속 구현: 기존 workspace 안의 영구 코어 기반

독립 workspace를 추가하지 않고 `apps/web/src/features/exam-coach` 아래에 제품 경계가 분명한 도메인 코어를 다시 구현했다. 기존 영어 학습 DB·인증 모델을 참조하지 않으므로 데이터 경계는 유지하면서 `pnpm-lock.yaml` importer 문제를 피한다.

이번 후속 구현에서 저장소에 남기는 기반은 다음과 같다.

- 2026 Q-Net 적용기간과 공식 12개 영역·세부 토픽 레지스트리
- SQL·C 선수지식 그래프
- SQL·C 6개 기술쌍의 18분 기준선/종료 동형 진단
- 중복 방지 `eventId`, 오답·힌트 사용 `Again`, 첫 제출 전용 FSRS 입력 계약
- 목표 기억률 `0.9`를 가진 FSRS 어댑터 경계
- SQL·C 샘플 콘텐츠와 스키마 검증 테스트

### 6.1 콘텐츠 JSON Schema

콘텐츠의 런타임 단일 계약은 Zod 스키마로 두고, 편집기·외부 도구에서 사용할 Draft 2020-12 JSON Schema를 함께 저장한다. 저장된 JSON Schema와 런타임 스키마는 필수 필드, 공식 영역, 지식 유형, 검수 상태, 기억 이력 승계 값이 일치하는지 테스트한다.

채점 규칙은 `exact`, `keywords`, `sql` 전략을 구분하고 각 전략에 필요한 허용 답안·필수 키워드·필수 SQL 절을 검증한다.

### 6.2 별도 검수 승인 계약

`reviewed` 상태는 단순 문자열 변경으로 만들지 않는다. 승인 함수가 다음 조건을 만족할 때만 검수 메타데이터와 함께 생성한다.

- 검수자는 작성자와 달라야 한다.
- 검수한 콘텐츠 버전과 현재 버전이 같아야 한다.
- 정답, 해설, 공식 범위, 허용 답안, 난이도 체크리스트가 모두 완료돼야 한다.
- 콘텐츠를 개정하면 버전을 올리고 기존 검수 승인을 제거하며 `draft`로 되돌린다.
- 개정 시 기억 이력 승계 여부는 자동 결정하지 않고 `undecided`로 되돌린다.

이 계약은 기존 workspace의 일반 `pnpm test`에 포함되므로 별도 패키지나 lockfile 변경 없이 CI에서 함께 검증된다.

### 6.3 게스트 로컬 이벤트 저장과 재생

브라우저 게스트 학습의 영속화 경계도 기존 서비스 데이터와 분리된 `exam-coach:v1:*` namespace로 구현한다.

- 게스트 ID는 `crypto.randomUUID()`를 기반으로 한 비식별 로컬 ID를 한 번 생성해 재사용한다.
- 장기 저장 대상은 답안 원문이 아니라 검증된 `LearningEvent`뿐이다.
- 이벤트 저장 envelope에 schema version과 learner ID를 함께 기록해 다른 게스트의 이력을 섞지 않는다.
- 같은 `eventId`의 완전히 동일한 재전송은 멱등 처리한다.
- 같은 `eventId`인데 payload가 다르면 데이터 충돌로 거부한다.
- 로드 시 각 이벤트를 다시 검증하고 발생 시각 순으로 정렬해 결정적으로 재생한다.
- 손상되거나 다른 learner의 저장 데이터는 조용히 신뢰하지 않고 명시적으로 오류 처리한다.
- 게스트 데이터 초기화 시 ID와 학습 이벤트를 함께 삭제한다.

다음 우선순위는 이 이벤트 재생 결과를 실제 유지보수되는 FSRS 구현체에 연결해 기억 상태를 재계산하는 것이다.

### 6.4 FSRS 기억 상태 재계산 계약

실제 알고리즘 구현을 저장소에 임의 복제하지 않고, 이벤트 로그를 FSRS 어댑터에 결정적으로 재생하는 경계를 먼저 고정했다.

- 이벤트는 `eventId` 기준으로 중복 제거하고 충돌 payload는 거부한다.
- 첫 제출 이벤트만 카드 기억 일정 갱신에 사용한다.
- 입력 순서와 무관하게 `occurredAt` 순으로 재생한다.
- 각 이벤트의 `fsrsVersion`에 맞는 어댑터를 resolver로 선택한다.
- 어댑터 버전 불일치, 잘못된 카드 ID, 잘못된 기억 상태 버전은 오류로 거부한다.
- 해당 카드의 첫 제출 이벤트가 없으면 기억 상태는 `null`로 유지한다.

현재 `ts-fsrs`는 package/lockfile에 포함되어 있지 않으므로 다음 단계는 저장소 의존성 정책을 통해 검증된 FSRS 구현체를 추가하고 이 resolver에 연결하는 것이다.

### 6.5 시간 제한 오늘 큐

FSRS 기억 상태가 준비됐을 때 UI가 바로 소비할 수 있도록 오늘 학습 큐의 결정적 계약도 추가했다.

- `dueAt`이 현재 시각 이하인 카드만 만기 복습 대상으로 본다.
- 만기 복습은 기억 위험도, 더 오래된 만기 시각, 콘텐츠 중요도 순으로 정렬한다.
- 하루 학습 시간 예산을 초과하는 항목은 큐에 넣지 않는다.
- 만기 복습이 하나라도 예산 때문에 밀리면 신규 학습을 추가하지 않는다.
- 신규 학습은 모든 선수 개념이 숙달된 경우에만 열린다.
- 이미 숙달된 개념의 신규 카드는 다시 넣지 않는다.
- 신규 카드는 커리큘럼 순서를 먼저 지키고 같은 순서에서는 중요도를 사용한다.
- 큐 결과에는 사용 시간, 남은 시간, 만기 복습 수, 밀린 만기 복습 수를 함께 반환한다.

### 6.6 규칙 기반 채점 엔진

콘텐츠의 검수된 `grading` 계약을 그대로 실행하는 결정적 채점 엔진을 추가했다.

- `exact`는 Unicode 정규화, 앞뒤 공백 제거, 연속 공백 축약과 대소문자 정규화 뒤 허용 답안과 비교한다.
- `keywords`는 검수된 필수 키워드가 모두 포함돼야 정답으로 판정한다.
- `sql`은 문자열 리터럴 밖의 SQL 구조만 대문자·공백·구두점 기준으로 정규화하고 문자열 리터럴의 값과 대소문자는 보존한다.
- SQL 필수 절은 모두 포함돼야 하며 `DELETE`, `UPDATE`, `INSERT` 같은 금지 토큰은 실행 가능한 토큰 위치에서만 차단한다.
- 금지 토큰 문자열이 컬럼명 일부나 SQL 문자열 리터럴에 들어간 경우에는 오탐하지 않는다.
- 채점 실패 시 허용 정답 자체를 결과에 노출하지 않으며 채점 결과에도 제출 답안 원문을 저장하지 않는다.
- 잘못된 채점 계약을 가진 콘텐츠는 채점을 시도하지 않고 오류로 거부한다.

### 6.7 첫 제출·교정·점진적 도움 흐름

규칙 기반 채점 결과를 학습 세션으로 연결해 최초 독립 수행과 이후 교정을 분리했다.

- 첫 제출 전에는 교정 제출과 힌트 공개를 모두 차단한다.
- 첫 제출에는 정오, 응답시간, 채점 결과만 남기고 사용자가 작성한 답안 원문은 세션 상태에 저장하지 않는다.
- 첫 제출은 한 번 기록되면 이후 교정 정답으로 덮어쓰지 않는다.
- 오답 뒤 도움은 `개념 단서 → 구조 힌트 → 구체적 힌트 → 해설·정답` 순서로 한 단계씩 공개한다.
- 정답을 독립적으로 맞힌 첫 제출에는 점진적 힌트를 열지 않아 이미 성립한 독립 회상을 훼손하지 않는다.
- 교정 제출은 횟수와 최신 채점 결과만 별도로 반환하며 최초 정오를 변경하지 않는다.
- 첫 제출이 오답이거나 도움을 사용한 세션은 요청 등급과 무관하게 학습 이벤트를 `Again`으로 강제한다.
- 도움 없이 첫 제출에 성공한 경우에만 `Hard`, `Good`, `Easy`를 학습 이벤트에 기록할 수 있다.
- 콘텐츠 ID와 버전이 세션 시작 시점과 달라지면 해당 세션의 제출·피드백을 거부한다.
- SQL·C 기준 콘텐츠에는 3단계 점진적 힌트를 추가하고, 4단계는 기존 검수 대상인 해설·정답을 재사용한다.

### 6.8 개념 숙달 증거와 준비도 리포트

카드별 FSRS 기억 상태와 개념 수준의 숙달 근거를 하나의 점수로 합치지 않고 별도 축으로 집계하는 코어를 추가했다.

- 이해, 회상, 적용, 실전 평가를 서로 다른 `MasteryEvidence` 유형으로 기록한다.
- 오답·도움 사용 이력은 증거로 남기되 독립 수행 성공으로 계산하지 않는다.
- 각 개념은 시도 수, 독립 시도 수, 독립 정답 수, 독립 성공률, 최근 독립 성공 시점을 유형별로 유지한다.
- 연결된 카드의 기억 상태는 카드 수, 만기 복습 수, 다음 만기 시각으로 별도 요약한다.
- 독립 회상 반복 실패, 반복 도움 의존, 적용 실패, 복습 부채를 명시적인 취약 신호로 반환한다.
- 준비도 리포트는 공식 영역별 개념 커버리지, 독립 회상률, 독립 적용률, 실전 평가 성과, 복습 부채를 각각 표시한다.
- 증거가 없는 비율은 임의 값을 만들지 않고 `null`로 유지한다.
- 리포트에는 합격 확률을 만들지 않으며 실제 관찰된 증거와 측정 시점만 반환한다.
- 동일 evidence ID의 재전송은 멱등 처리하고 payload가 다른 충돌은 거부한다.
- 하나의 학습 이벤트가 여러 개념에 연결될 때는 `eventId:conceptId` 형태의 독립 evidence ID로 펼쳐 다중 개념 문항의 증거 충돌을 막는다.
- 현재 커리큘럼에 등록되지 않은 concept ID의 증거는 전체·영역 준비도 비율에서 제외한다.
